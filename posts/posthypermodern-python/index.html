Post-Hypermodern Python - setting up a Python monorepo in 2026

Inspiration

This post is inspired by Hypermodern Python by Claudio Jolowicz. It was 100% my “go-to” guide for setting up (some parts of) Python projects, but it’s gotten a bit outdated. Here’s my version of that, updated to 2026, with monorepos, and the tooling I ended up using.

Why

Well, someone asked my for how I set up the Python monorepo at work (Opsin Security). Instead of DMing them, decided to write a post.

What

  • I want a single shippable artefact (remember that a Docker image is a shippable artefact) to ship; Meaning, there’s no “services”. In this case, you can have just a single package.
  • I want multiple shippable artefacts; Meaning, multiple services, each with their own package.

We’re going to focus on case 2 but it’s very easy to simplify from case 2 (multi-package) to case 1 (single-package).

To make things concrete, instead of naming things package-a and package-b, let’s assume we’re building something with two services: 🐶 fetcher (it fetches data) and 🛠 ️processor (it processes said data).

The important thing to notice is that while these two packages are distinct, they do share a few things. Starting “from the left” (development) all the way to “the right” (deployment):

Development practices are the same; no need to manage two versions of linters or formatters. This doesn’t mean necessarily the same config (same lint rules), but same tooling. You can imagine that in our example, the 🐶 fetcher has a bit more relaxed linting rules than the 🛠 ️processor because it deals with 3rd party APIs and therefore trying to make it too strict would just be annoying.

Single CI/CD pipeline. In my experience, better to have a single pipeline even for microservices that are TRULY shipped independently, which is pretty rare anyways. Because the lint, test, build flows are usually the same, it’s better to have a single, reusable pipeline.

Dependency management - what do we want to achieve?

    processor[Processor service]
    processor --> common
    fetcher --> common
